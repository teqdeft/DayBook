Daybook Phase 1: Build Guide
Sep 30, 2026 · ​@Teqdeft
1. Overview
Phase 1 replaces the "post in Slack, PM copies to a sheet" routine with one web app,
Daybook. Everyone checks in, logs their day and submits a daily report there. PMs, HR and
the CEO see it live, and reports still post to Slack in the same format.
The approved screens are on the Daybook Phase 1 design canvas. This guide is the build
spec for those screens: build the UI to match the canvas exactly.
Goals
1. Every employee checks in, checks out and submits a daily report in Daybook.
2. PMs see who worked on what, and for how long, without reading Slack.
3. HR sees daily attendance and fixes mistakes with a saved reason.
4. The code is simple enough for any developer on the team to pick up, and later phases
plug in without rework.

Done when
For 2 straight weeks, every daily report comes through Daybook.
PMs stop collecting updates from Slack by hand.
HR can answer "who was in, when, and where" for any day from the Attendance
screen.
Assumptions: 25 to 30 people, one office, India time (IST), Monday to Friday, 9:30 AM to
6:30 PM. All of these are settings, not hard-coded values.
2. Roles and permissions
There are four roles: employee , pm , hr and admin . Each user has exactly one role. PMs
and HR also check in and submit reports like everyone else. The CEO has the admin role,
and check-in is optional for them ( tracks_attendance = false ).
Permissions are checked on the server for every request. The UI only hides what a role
can't use; it never decides access.

Principles
1. Simple over clever. No ORM models, no Redux, no GraphQL, no microservices. React
state and fetch are enough at this size.
2. Features live in modules. Each feature (attendance, reports, projects and so on) has
its own folder with the same three files. Section 4 shows the pattern.
3. Thin routes, logic in services. API routes only read input, check permission, call a
service and return JSON. Pages never contain SQL.

4. The server owns time. Check-in and check-out times come from the server clock,
never the browser. All timestamps are stored in UTC; each record also stores its
work_date in the company time zone.
5. Settings, not constants. Office hours, lock time, working days and Slack options are
rows in the settings table, editable by Admin.
6. Every change is traceable. Report edits keep revisions; attendance corrections, role
changes and project changes write to audit_logs .
7. Slack never blocks the user. The web app writes Slack messages to an outbox table;
the worker sends them and retries on failure.
How a request flows
Pages are React Server Components. They read the session, then call module services
directly (no HTTP hop).
Buttons and forms are small Client Components. They call /api/... routes with
fetch , then call router.refresh() to redraw the page with fresh data.
The worker imports the same module services, so business rules exist in one place.
4. Project structure
One repository, organised by feature. Pages and API routes sit in src/app , business logic
sits in src/modules , and shared helpers sit in src/lib .

The module pattern. Every module has the same files, so a new developer knows where
to look.
A route stays this small:
// src/app/api/attendance/check-in/route.js
import { withRoute } from '@/lib/route';
import { attendance } from '@/modules/attendance';
import { checkInSchema } from '@/modules/attendance/schemas';
export const POST = withRoute({ permission: 'attendance.self', body: 
checkInSchema },
  async ({ user, body, ip }) => attendance.checkIn({ user, ip, ...body })
);
withRoute does the same five things for every endpoint: loads the session, checks the
permission, validates input with zod, runs the handler, and turns errors into the standard
JSON error shape. It also logs each request with its duration.
Naming. Database tables and columns use snake_case ; JavaScript uses camelCase . The
Knex config converts between them once, with wrapIdentifier and
postProcessResponse , so no code does it by hand.
Adding a feature later always means the same steps: a new folder in src/modules , a new
migration, new permission keys, a nav entry in config/navigation.js , and new routes.
Existing modules don't change.

Rules
Only src/lib/env.js reads process.env . Everything else imports the parsed env
object.
Nothing secret starts with NEXT_PUBLIC_ , so no secret can reach the browser.
Values the business changes (office hours, report channel, working days) are in the
settings table, not here.
Development, staging and production each have their own values and their own Slack
app redirect URL.
6. Database schema
Phase 1 uses 19 tables in five groups, all InnoDB with utf8mb4_unicode_ci . Every table
has id BIGINT UNSIGNED AUTO_INCREMENT as primary key (except join and settings
tables) and created_at / updated_at as DATETIME in UTC, unless noted.
Conventions
Times are DATETIME in UTC. Dates that mean "which working day" are DATE in the
company time zone and always named work_date .
Durations are whole minutes ( minutes , late_minutes , total_minutes ). The UI
shows hours; 1.5h is stored as 90 .
Status values are ENUM s so bad values can't get in.
Foreign keys are real constraints. Users are never deleted, only deactivated.

7. Business rules
These rules live in the module services and nowhere else. Every value in bold italics below,
like 9:30, comes from settings , not code.
7.1 Time and working days
The company time zone is Asia/Kolkata. work_date is the local date at the moment of
check-in.
A working day is a weekday listed in working_days (Monday to Friday). Holidays arrive
in Phase 2.
All "now" values come from the server clock through src/lib/time.js .
7.2 Check-in
1. One check-in per person per work_date . A second try returns ALREADY_CHECKED_IN .
2. The server compares the client IP with office_networks . On a match, the only option
is Office and office_verified = 1 .
3. On any other network, the default is WFH. If allow_unverified_office is on, the person
can pick "I'm in the office, but the Wi-Fi is down". That saves location = office ,
office_verified = 0 , and notifies HR.
4. On a working day, if the local check-in time is after late_after (or the person's own
shift_start ), late_minutes is the difference in whole minutes. Otherwise it is 0.
Phase 1 only records it.

5. Check-in on a non-working day is allowed and saved with is_working_day = 0 .
6. An optional note (up to 255 characters) goes to the PM, for example "plumber visit,
online by 11".
7. Forgot to check in earlier? The person checks in now, then taps "I came earlier" to send
a correction request with the real time.
7.3 Check-out
1. Check-out needs an open check-in for today. It saves the server time and sets
checkout_status = checked_out .
2. If today's report is not submitted, the API still checks out but returns reportPending:
true . The UI then shows "Write your report" with "Check out anyway" as the second
button.
3. The gap warning appears when present time and logged hours differ by more than 90
minutes. It warns, never blocks.
4. At 00:05 the worker marks any check-in still open from the day before as missing . HR
fixes it from Attendance.
7.4 Daily report
1. Opening the report page creates today's report as a draft if none exists.
2. The draft starts with carry-over: every in_progress or blocked task from the
person's latest submitted report, grouped under its project (only if the project is still
active), with 0 hours. Each carried task keeps its first_reported_on .
3. The project picker lists urgent projects first (with the Urgent label), then the person's
projects, then all other active projects by search. A pending project request can also
be picked; it shows "Waiting for approval".
4. Drafts autosave one second after the last change.
5. Submitting needs: at least one project; each project with hours above 0 in 0.25-hour
steps and at least one task; tasks 2 to 500 characters; no project twice; a daily total of
16 hours or less.
6. On submit: revision goes up by one, a snapshot goes to report_revisions , and a
Slack message is queued. The first submit posts a new message; later submits update
the same message using slack_ts .
7. Lock. locks_at is set to 12:00 the next day in company time. Until then the person
can change the report; every save after the first submit is a new revision.

8. After the lock, the report is read-only. The person sends an edit request with a reason.
The approver (section 2) approves or declines. Approval sets unlocked_until to 24
hours later and notifies the person. The next submit clears it.
9. A forgotten day can be added until its lock time. After that, the person sends an edit
request for that date and the report is created on approval.
7.5 Carry-over and stuck tasks
A carried task copies the title, status and first_reported_on , and links back with
carried_from_task_id .
A task is stuck when it is still in_progress and at least 5 working days have passed
since first_reported_on . Stuck tasks show under "Tasks to watch" on the employee
detail page.
7.6 Urgent projects
Only the project's PM or Admin marks a project urgent, and a note (up to 200
characters) is required.
Marking urgent notifies every member in the app, and by Slack DM if
slack_urgent_notify is on. The project then shows on each member's Today screen, at
the top of the report picker, and on the PM dashboard.

Sign-in steps
1. The Sign in with Slack button goes to /api/auth/slack/start . It creates random
state and nonce values, keeps them in a 10-minute httpOnly cookie, and redirects to
Slack's authorize page with the scopes openid email profile , the redirect URL
APP_URL/api/auth/slack/callback , and team=SLACK_TEAM_ID .
2. Slack sends the person back to /api/auth/slack/callback with a code . The server
checks state , exchanges the code for tokens, and reads the user info (email, name,
picture, Slack user ID, workspace ID).
3. The server rejects the sign-in if the workspace isn't SLACK_TEAM_ID , the email isn't in
users , or the user is deactivated. The person lands back on /login with a clear
message.
4. On success, it saves slack_user_id , avatar_url and last_login_at , creates a
session, and redirects to / (which picks the start page by role).
Sessions
The cookie holds a random 32-byte token. The database stores only an HMAC-SHA256
hash of it ( token_hash ), keyed with SESSION_SECRET , so a leaked database can't be
used to sign in.
Cookie settings: httpOnly , secure in production, sameSite=lax , path=/ .
Sessions last SESSION_TTL_DAYS (30). When fewer than 7 days are left, the next
request extends it. last_seen_at updates at most every 5 minutes.
Logout deletes the session row and the cookie. Deactivating a user deletes all of their
sessions. A daily job removes expired sessions.
Access checks
middleware.js only checks that the cookie exists and redirects to /login if it
doesn't. It can't reach MySQL, so it never decides access.
The (app)/layout.js loads the user from the session. Each page calls
requirePage('permission.key') at the top.
Every API route declares its permission in withRoute . Services also check ownership:
a report belongs to its owner, and a PM's project.manage applies only to projects
where they are pm_id .
can(user, key) in src/lib/permissions.js is the single place that answers "is this
allowed".

Repos take an optional trx so services can wrap several writes in
db.transaction(async (trx) => { ... }) . Any write that touches more than one
table uses a transaction.
Services convert units at the edge: the API accepts hours, the service stores minutes.

Errors
Throw new AppError(code, { message, status, fields }) for expected problems.
Each code has a default status and message in src/lib/errors.js , for example
ALREADY_CHECKED_IN (409), REPORT_LOCKED (409), NOT_FOUND (404), FORBIDDEN
(403), VALIDATION_FAILED (400).
Anything else becomes a 500 with a generic message. The real error is logged with a
request ID, and the response includes that ID so it can be found.
Validation: every body and query goes through its zod schema in schemas.js . Query
numbers are coerced ( z.coerce.number() ). Error messages are written for people:
"Hours must be above 0", not "Expected number > 0".

15.2 Performance
At 30 people the load is tiny; the goal is to stay fast at 500 without changes.
HTTPS everywhere; HTTP redirects to HTTPS.
Sign-in limited to one Slack workspace and to active users HR has added.
Session tokens hashed in the database; cookies httpOnly , secure , sameSite=lax .
Every API route declares a permission; services check ownership.
Mutations check the Origin header.
All input validated with zod; all SQL through Knex bindings (no string-built SQL).
Sign-in routes rate-limited to 10 attempts per minute per IP.
Client IP read from X-Forwarded-For only when TRUST_PROXY=true .
Secrets only in environment variables; nothing secret uses NEXT_PUBLIC_ .
Security headers set in next.config.mjs : X-Frame-Options: DENY , Referrer-
Policy: strict-origin-when-cross-origin , X-Content-Type-Options: nosniff .
Attendance corrections, role changes, settings changes and project changes write to

The database user has only the rights the app needs; migrations use a separate admin
